# MIDI Loopback module sketch

Original sketch: 7 October 2026, based on `6f9e5bc9`. Updated 12 October:
CHAN-press routing, native Part persistence and the track-generated channel
message families are implemented. Remaining hardware and lifecycle acceptance
items are identified in the README; the design below records the contract. [README.md](README.md) defines the tested implementation boundary.
No hardware acceptance is claimed.

MIDI Loopback lets selected MIDI tracks control the Octatrack's own audio
side through its existing MIDI receive behaviour. A MIDI track becomes an
extra sequencer and modulation source for audio tracks, while the physical
MIDI ports remain available for external instruments.

## Playing workflow

Implemented access: press `A: CHAN` on MIDI NOTE SETUP to apply the staged
channel and open ROUTING; `A: DEST` selects EXT/INT/BOTH. The native Part owns
the setting. See README.md for the implemented scope and remaining boundaries.

| DEST | Result |
|---|---|
| EXT | Existing external output. Default for every track. |
| INT | Deliver the track's messages internally; suppress their external transmission. |
| BOTH | Deliver one internal copy and retain normal external transmission. |

`CHAN` keeps its normal meaning. Set an audio track's receive channel to the
MIDI track's output channel. There is no fixed M1-to-T1 pairing: several MIDI
tracks can control one audio track, and existing receive assignments decide
which audio tracks respond. `CHAN OFF` still disables output.

Example: audio T1 receives channel 1. MIDI M1 uses channel 1, `DEST INT`,
and CC 46 in one CTRL slot. Its trigs, parameter locks and MIDI LFO can
change T1's level. M1 could run a 15-step pattern against T1's 16-step rhythm.
M2 could address the same channel with a different CC; M3 could remain `EXT`
to play a synthesizer.

## Control coverage

The contract is the audio-side response to MIDI, not a new parameter map.
Route the normal channel messages generated by a MIDI track without a
handpicked CC whitelist. Notes, releases, CCs, pitch bend, pressure and
program change retain whatever meaning the receiver already gives them.
An unsupported message gains no new function just because it is internal.

This covers existing parameter CCs, level, balance, mute, cue, recorder
commands and note-map actions, plus shared controls such as the crossfader
and scene selection. Mapping extensions in the selected firmware should be
reached through the same dispatch path; compatibility must be tested.
Program change is a project/pattern operation, not a per-audio-track knob,
and needs its own receive-setting and feedback tests.

Audio CC IN, AUDIO NOTE IN, receive channels, note maps and other relevant
receive settings remain authoritative. Audio voices keep their existing
pitch range and polyphony. This does not add MIDI mappings or turn an audio
track into a polyphonic synth.

Clock, Start, Continue, Stop, song position and SysEx are outside the initial
internal route. Their external behaviour stays unchanged. Pressing STOP
must still deliver the resulting note releases to their original destinations.

Auto-channel behaviour follows the existing mode and selection rules; it
does not mean “always control the selected audio track.” Explicit audio
receive channels are the first test configuration.

## Behaviour that must remain predictable

- Capture notes after the MIDI track's transpose, arp and installed note
  processing, so internal and external destinations receive the same final
  musical events. Cover sequenced and live trig-key paths separately.
- Preserve stock mute behaviour, including any distinction between notes
  and CC/LFO output. Loopback must not generate events stock would suppress.
- Parameter changes have the same Part, live-state and recording effects as
  external MIDI. They are not a separate temporary modulation layer.
- Existing audio parameter locks, scenes and LFOs still act on the track.
  Measure their ordering against incoming MIDI; do not promise that internal
  CCs override an audio lock on the same step.
- EXT is the bypass baseline. INT and BOTH must preserve release ownership
  across destination/channel edits, pattern or Part changes and project loads.
  Release old destinations before replacing the route; do not send a held
  note's release only to the newly selected destination.

## Firmware approach

Use a ColdFire module with linked code and a bounded queue in the declared
DRAM reserve. No DSP effect slot is needed. Queue complete messages, retaining
source MIDI track, route at emission and origin information until delivery.
Do not call the audio receiver synchronously from the sequencer interrupt.

```text
MIDI track note and controller producers
    -> final event plus source track
    -> destination routing
         -> existing external send path for EXT and BOTH
         -> internal message queue for INT and BOTH
              -> MIDI task dispatch and existing receive handlers
                   -> audio commands and parameter updates
```

Known entry points are evidence for the approach, not final hook claims:

| Existing path | Evidence and implication |
|---|---|
| `midi_send`, `0x40010bc8` | USB-MIDI hooks this sender. Useful for tracing output, but source-track identity and coverage of every producer are not established here. |
| `midi_rx_enqueue`, `0x40092bbc` | USB-MIDI feeds this byte receiver. Demonstrates an internal input path; blindly mixing a second byte stream with DIN running status or an unfinished message is not a safe design. |
| MIDI task `0x40005540`, queue `0x46c7e974` | Dispatches completed messages through `0x400d6474`. Candidate delivery boundary; message ownership, wakeup and origin propagation still need tracing. |
| CC handler `0x4000e79c` | Reuses channel mapping and posts audio parameter events to the main task. Enter through the installed dispatcher so module extensions can participate. |
| CC timer `0x400409f4` | Documented CC output uses a channel/CC cache and bitmap. Prove sequencer CC and LFO paths individually; a sender hook alone cannot be assumed to cover them. |

The first investigation must trace notes, note-offs, live keys, arp, CC
locks, CC LFOs, pitch bend, pressure and program change from their producers.
If source identity disappears when messages are coalesced by channel and CC,
route before that point. Preserve the existing external collision/coalescing
rules; establish internal ordering for two tracks addressing the same CC.

The stock audio receive path already has channel-priority rules, and the CC
handler can forward some input back to output. A global copy of every outgoing
message would therefore be insufficient for the per-track contract.

## Feedback and queue limits

Only original events from selected MIDI-track producers qualify for internal
routing. Received MIDI, audio-knob feedback and responses such as CC send
requests must not automatically become new loopback sources. Trace delayed
echoes as well as immediate calls: a boolean guard around the send routine
does not protect work posted to another task and executed later.

The internal queue needs bounded work per service pass, high-water and drop
counters, and an explicit overflow policy. Drops must be whole messages.
Reserve capacity for releases or provide a proven cleanup path for notes
owned by loopback; do not silently discard releases and leave held notes.
Cleanup must not release unrelated externally held notes.

Program changes and MIDI-triggered actions can themselves start new sequence
events. Test those causal cycles explicitly; “one copy per send call” alone
does not prove that feedback is bounded. Unresolved cycles block that delivery
path from being declared complete.

## Module compatibility and settings

USB-MIDI already claims the `0x40010bc8` sender entry. A second detour there
would conflict. Prefer producer-side routing that leaves the shared sender
intact, or design explicit shared integration if tracing proves it necessary.
For INT, suppress the source event before both DIN and USB mirrors; for BOTH,
retain the normal configured external outputs without adding a second mirror.

Check Harmony, Follow and Scales on their module branches and on the combined
remix. Loopback must receive their final events once and must not feed those
events back through their incoming-note processing for another transformation.

Implemented setting scope is eight destinations per native Part, default EXT,
without parameter locks. Native Part/project Save/Reload and copy carry the
shared flags byte; no private on-card format or OTX dependency is introduced.

## First prototype and verification

Start with M1 on channel 1 targeting T1, volatile routing, one CC 46 change
and one chromatic note with its release. Compare the resulting receiver events
and audio state with the same messages injected through normal MIDI input.
This is the first milestone, not the full feature boundary.

Then extend the evidence in this order:

1. **Routing:** EXT, INT, BOTH, CHAN OFF, mismatched channels, two sources on
   one channel, multiple audio listeners, auto channel in both UI modes.
   Check internal delivery count and DIN/USB output independently.
2. **Control coverage:** every generated channel-message family, every stock
   audio CC family, each supported note map, receive OFF settings, global
   controls and installed mapping extensions. Verify observable state changes,
   not just queue writes.
3. **Lifecycle:** stop/double-stop, mute/unmute, arp, live notes, destination
   and channel changes while held, Part/pattern/project transitions, and
   eventually settings save/reload/copy.
4. **Feedback and load:** audio CC output, CC direct connect, send requests,
   program changes, simultaneous DIN/USB input and dense eight-track CC/LFO
   traffic. Verify bounded queue growth and release recovery under overflow.
5. **Integration and timing:** standalone and combined remix gates, then
   hardware MIDI capture and recorded audio. Measure jitter and ordering
   against a physical loopback cable; internal routing need not emulate DIN
   serialization latency, and emulator success is not hardware timing proof.

Use the existing verification harness to compare normal MIDI input and internal
delivery with the same fixtures. If a helper is needed by several module gates,
keep it in shared MIDI verification support rather than importing another
module's verifier.
